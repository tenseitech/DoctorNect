## 4. Root Cause Analysis: The Core Architectural Blockers Unresolved for a Week

### Rank 1: Dual-Database Identity & Custom Claims Race Condition (Firebase Auth vs Supabase RLS)
- **Evidence:**
  - [supabase_bootstrap.dart:60-65](file:///c:/Users/khije/Downloads/DoctorNect/doctor/frontend/lib/core/supabase/supabase_bootstrap.dart#L60-L65): `if (role != 'authenticated') throw MissingSupabaseClaimException(...)`
  - [registration_otp.js:2986-2992](file:///c:/Users/khije/Downloads/DoctorNect/doctor/backend/functions/registration_otp.js#L2986-L2992): Cloud Functions sets `{ role: 'authenticated', app_role: normalized }` on user documents.
  - [firebase_auth_service.dart:312-325](file:///c:/Users/khije/Downloads/DoctorNect/doctor/frontend/lib/core/firebase/firebase_auth_service.dart#L312-L325): Calls `signInWithCustomToken(customToken)`, but does NOT immediately invoke `await user.getIdToken(true)` to force refreshing claims into the client session.
- **Root Cause:** In Supabase PostgreSQL, all RLS policies are granted `TO authenticated`. PostgREST validates the bearer JWT and only assigns the `authenticated` database role if the token payload contains claim `role: "authenticated"`. Default Firebase Auth tokens do not include this claim. Setting custom claims via Firebase Admin SDK is asynchronous. When a user logs in, if Supabase queries execute before the client token refreshes, PostgREST falls back to the `anon` PostgreSQL role, resulting in **queries silently returning empty arrays (`[]`) or throwing HTTP 403 `FORBIDDEN`**.
- **Impact:** This was the primary reason the cutover flag was kept off for a week; developers observed sporadic `MissingSupabaseClaimException` or empty tables whenever testing Supabase mode directly.
