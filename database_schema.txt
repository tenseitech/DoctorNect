================================================================================
1. ARCHITECTURE OVERVIEW & IDENTITY MODEL
================================================================================
DoctorNect uses Google Cloud Firestore as its primary document database. Data is
organized into top-level collections partitioned by operational domain and actor roles,
with subcollections used for tightly coupled or private subordinate entities.

Key Identity Principles:
- Every authenticated user has a Firebase Authentication record with a unique UID.
- The root document `users/{uid}` establishes the account's role (`doctor`, `patient`,
  `medicalStore`, `lab`, `ambulance`, or `super_admin`) and references the primary
  profile document through `profileId`.
- Profile IDs follow standardized formats:
  * Doctors: "d1", "d2", or custom alphanumeric IDs
  * Patients: "p{timestamp}" for registered patients, "wi{timestamp}" for clinic walk-ins
  * Medical Stores: "ms_{timestamp}" or alphanumeric IDs
  * Labs: "lab_{timestamp}" or alphanumeric IDs
  * Ambulances: Driver username or alphanumeric IDs
- Role escalation is strictly prohibited by Firestore rules: once a user document is
  created, its `role` cannot be mutated by client requests.
- Admin verification (`verified: true`) is required for healthcare providers (Doctors,
  Pharmacies, Labs, Ambulances) before appearing in public directories or accepting
  bookings.

================================================================================
2. USER ROLES & PERMISSION MATRIX
================================================================================
Roles supported in `users/{uid}.role`:
1. "patient":
   - Can read own patient profile, family members, health records, lab bookings.
   - Can read verified doctors, verified stores, verified labs, available ambulances.
   - Can create appointments, lab bookings, ambulance broadcasts, reviews, support tickets.
2. "doctor":
   - Can read/edit own profile and availability schedule.
   - Can create prescriptions, lab orders, doctor referrals, pharmacy delivery dispatches.
   - Can read patient clinical data only if patient has opted-in and doctor is on care team
     (or for clinic walk-ins).
   - Can add to community catalog (medicines, diagnoses, lab tests, radiology).
3. "medicalStore" (Pharmacy):
   - Can read/edit own store profile and drug license details.
   - Can receive and fulfill pharmacy deliveries from connected doctors.
   - Can manage doctor-store B2B connections.
4. "lab" (Diagnostic Laboratory):
   - Can read/edit own diagnostic lab profile.
   - Can receive lab orders from doctors and lab bookings from patients.
   - Can upload diagnostic lab reports and update order/booking statuses.
   - Can create counter walk-in bookings.
5. "ambulance":
   - Can manage ambulance driver listing and vehicle equipment options.
   - Can receive ambulance dispatch requests and accept emergency broadcasts.
   - Private credentials (PIN / FCM) stored in isolated subcollection.
6. "super_admin" / "superAdmin" / "admin":
   - Full read/write access to verify providers, review audit logs, and manage system configs.
   - Accounts explicitly white-listed in Firestore security rules.

3.1 abuse_rate_limits
--------------------------------------------------------------------------------
Path: /abuse_rate_limits/{bucket}
Purpose: Backend sliding-window rate limiting for IP, user, and phone buckets.
Access: Admin SDK / Cloud Functions only (read/write: false in client rules).

Fields:
- count (number, required): Number of attempts within the current time window.
- windowStart (timestamp, required): Start time of current rate limit window.
- category (string, required): Category, e.g. "api", "login", "signup", "ai", "scrape", "payment".
- updatedAt (timestamp, required): Last modification timestamp.

- adminUid (string, required): Firebase Auth UID of performing admin.
- adminEmail (string, required): Email address of performing admin.

- targetType (string, required): Target entity category ("doctor", "patient", "medical_store", "lab", "ambulance").

- targetName (string, optional): Display name of target entity.
- details (string, required): Human-readable description of change.
- metadata (map, optional): Additional contextual parameters or previous/new state diff.
- createdAt (timestamp, required): Server timestamp of action.

--------------------------------------------------------------------------------
Path: /ambulance_broadcasts/{broadcastId}

- status (string, required): "pending" | "accepted" | "completed" | "cancelled".
- acceptedDriverId (string, optional): Ambulance ID of the claiming driver.
- acceptedDriverName (string, optional): Name of driver who accepted.
- acceptedDriverPhone (string, optional): Phone number of driver who accepted.
- acceptedVehicleNumber (string, optional): License plate of dispatched ambulance.
- acceptedAmbulanceType (string, optional): Type of ambulance ("BLS", "ALS", "ICU", "Patient Transport").
- acceptedAt (timestamp, optional): Timestamp when driver claimed the request.
- rating (number, optional): Patient rating (1-5 stars, -1 for skipped).
- review (string, optional): Patient feedback text.
- createdAt (timestamp, required): Creation timestamp.
- updatedAt (timestamp, required): Last modification timestamp.

- pharmacy_connections & lab_connections:
  * B2B links pairing doctors/{doctorId} with medical_stores/{storeId} or labs/{labId}.

================================================================================
6. SECURITY & DATA PRIVACY CONSTRAINTS
================================================================================
1. Zero Public Database Access:
   - Direct database access is blocked without authentication (`isSignedIn()`).
   - App Check is enforced in production to block bot scraping and API abuse.
2. Clinical Data Isolation:
   - Prescriptions, lab orders, and health records are confidential.
   - Doctors can ONLY inspect a registered patient's records if:
     a) `patients.shareRecordsWithDoctors == true`
     b) The doctor is on the patient's `careTeamDoctorIds`, `primaryDoctorId`, or
        has an active link in `/patients/{patientId}/doctor_links/{doctorId}`.
3. Healthcare Provider Approval Gate:
   - Newly registered doctors start with `verified: false`.
   - Clinical write permissions (prescribing, referring, lab orders) are restricted
     to `isVerifiedDoctor()`.
   - Patients can only search and book verified doctors and accredited diagnostic labs.
4. Anonymous Review Sanitization:
   - Reviews contain sensitive patient names in `/reviews/{reviewId}`.
   - Public screens query `/review_public/{reviewId}`, where patient names are
     masked into initials (e.g. "Rahul Sharma" -> "R. S.") and direct patient UIDs
     are stripped out by serverless cloud triggers.
5. Isolated Driver Credentials:
   - Ambulance drivers authenticate via username and PIN.
   - Driver PIN and push tokens are strictly isolated in `/ambulances/{driverId}/private/settings`
     so public ambulance listings never expose authentication secrets or tokens.
